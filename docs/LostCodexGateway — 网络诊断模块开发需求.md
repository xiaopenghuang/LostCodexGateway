# LostCodexGateway — 网络诊断模块开发需求

## 一、开发目标

在现有 LostCodexGateway 项目中新增「网络诊断」模块。

该模块用于验证 Windows 本地电脑、SSH 网络隧道、Ubuntu 云服务器和 Codex 客户端之间的网络连接状态。

重点实现以下功能：

1. 检测本地 SSH 隧道是否正常运行。
2. 检测云服务器是否能够正常访问互联网。
3. 确认本地请求经过网关后的实际公网出口 IP。
4. 检测 Codex Desktop、Codex CLI 和 VS Code Codex 插件的实际网络路由。
5. 检查 DNS、IPv4、IPv6 和网络连接异常。
6. 识别网关断开、代理冲突和客户端连接失败等情况。
7. 提供可读的诊断报告和对应的故障处理建议。

模块应遵循最小权限原则，不读取 OAuth Token、API Key、Cookie、完整模型请求或用户聊天内容。

## 二、界面设计

在软件左侧导航栏中新增：

`网络诊断`

页面分为四个区域：

### 2.1 网络状态总览

展示以下项目：

| 检测项目 | 显示内容 |
|---|---|
| SSH 隧道 | 已连接 / 未连接 / 连接异常 |
| 本地代理 | 正常 / 不可用 |
| 云服务器 | 可连接 / 无法连接 |
| 出口 IP | 服务器公网 IP / 实际检测 IP |
| DNS | 正常 / 异常 / 未验证 |
| Codex Desktop | 已验证 / 部分验证 / 未验证 |
| Codex CLI | 已验证 / 部分验证 / 未验证 |
| Codex IDE 插件 | 已验证 / 部分验证 / 未验证 |

页面顶部放置「开始诊断」按钮。

检测完成后，以绿色、黄色、红色分别表示正常、需要注意和异常。

状态文字必须真实反映检测结果，不能仅因 SSH 隧道已连接就显示所有 Codex 客户端均已成功使用网关。

### 2.2 网络路径检测

以可视化方式展示：

Windows 本地电脑 → 本地网络网关 → SSH 隧道 → Ubuntu 云服务器 → 目标互联网服务。

每个节点显示连接状态、延迟和相关错误信息。

如果 SSH 隧道已经建立，但目标请求没有经过服务器，需要明确显示：

「SSH 隧道正常，但目标应用尚未验证使用该出口。」

如果实际请求使用的是其他代理节点，需要显示当前检测到的路由结果。

### 2.3 Codex 客户端诊断

分别展示：

- Codex Desktop
- Codex CLI
- VS Code Codex 插件

每个客户端独立显示运行状态、进程信息、路由检测结果和最近一次验证时间。

支持单独点击「检测」。

### 2.4 诊断日志

提供简洁的日志查看器，支持按检测项目、时间及错误级别筛选。

日志只记录必要的网络诊断信息，不记录聊天内容或认证凭据。

支持导出脱敏后的诊断报告。

## 三、核心功能实现

### 3.1 SSH 隧道检测

检测内容：

- SSH 子进程是否仍在运行。
- 本地 SOCKS5 监听端口是否可连接。
- SOCKS5 握手是否成功。
- 是否能够通过 SOCKS5 建立到测试目标的 TCP 连接。
- 是否存在连接超时、SSH 退出或本地端口冲突。

不能仅依靠 SSH 进程存在来判断隧道正常。

SSH 进程存活但 SOCKS5 连接失败时，应显示「隧道异常」。

SSH 断开时保留必要的错误信息，并通过现有连接管理模块执行受控重连。

### 3.2 出口 IP 检测

检测以下两种网络出口：

A. 本地默认网络出口。

B. 通过 SSH SOCKS5 隧道访问时的网络出口。

分别向可信的公网 IP 查询服务发送请求。

推荐使用：

https://api.ipify.org

https://api64.ipify.org

要求：

- 代理出口检测必须显式指定 SOCKS5，不得依赖系统代理设置。
- SOCKS5 测试需要使用远程 DNS 解析能力。
- 记录实际返回的 IP 地址及 IP 协议版本。
- 不得简单地把 SSH 服务器地址当作已经验证的出口 IP。
- 当服务器出口 IP 与预期不一致时，提示用户进行检查。
- IP 查询服务不可用时允许切换备用服务。

检测结果应显示：

本地出口 IP：xxx.xxx.xxx.xxx

网关出口 IP：xxx.xxx.xxx.xxx

预期服务器出口 IP：xxx.xxx.xxx.xxx

检测结果：匹配 / 不匹配 / 无法确认

用户可以手动配置预期出口 IP。

### 3.3 服务器连通性检测

通过现有 SSH 连接执行只读网络测试，检测：

- 服务器能否正常解析测试域名。
- 服务器能否建立对外 TCP/HTTPS 连接。
- 服务器对外连接是否超时。
- 服务器出口网络是否存在明显异常。

检测命令应设置超时时间，避免网络不通时无限等待。

不得修改服务器默认路由、防火墙、Docker 网络、Nginx 配置或 SSH 服务配置。

不得在未经用户同意的情况下安装服务器软件。

### 3.4 Codex 进程与流量检测

检测当前运行中的 Codex Desktop、CLI 和 IDE 插件相关进程。

使用 Windows 进程信息和 Mihomo 连接信息进行关联。

需要注意：

Codex Desktop 可能存在多个后台子进程。

Codex CLI 的实际可执行文件名称与路径需要根据安装方式确定。

VS Code 插件可能使用 VS Code 扩展宿主进程，不能仅根据 Code.exe 或 node.exe 就认定该连接一定属于 Codex。

因此，应采用：

进程信息 + 进程路径 + 连接信息 + 用户触发的测试请求

进行关联判断。

不得将所有 VS Code、Node.js 或浏览器流量自动认定为 Codex 流量。

### 3.5 实际路由验证

这是本模块的核心验收功能。

不能仅仅检查代理配置文件中是否存在 Codex 分流规则。

应结合 Mihomo 实际连接记录，检查目标应用是否命中网关出口。

支持以下状态：

- 已验证：观察到目标应用的相关连接通过指定网关，且出口检测符合预期。
- 部分验证：只确认了部分连接，仍有后台连接未确认。
- 未验证：没有足够证据判断实际路由。
- 路由异常：已观察到目标连接使用了非预期出口。

单条连接的验证结果不能自动推断为该客户端所有流量均已正确转发。

对于无法确定进程归属的连接，应显示「无法确认」，不得擅自归类。

如果使用 Mihomo，优先通过现有管理接口获取只读连接信息，不直接修改用户原有配置。

### 3.6 DNS 与 IPv6 检测

检查以下情况：

1. 本地与网关出口的 DNS 解析是否正常。
2. SOCKS5 请求是否使用预期的远程域名解析方式。
3. IPv4 和 IPv6 请求是否使用预期的网络路径。
4. 是否存在由于 IPv6 或其他网络配置造成的路由不一致。

SSH SOCKS5 不等于完整 VPN，因此不能仅凭 IPv4 测试结果认定所有 IPv6 和 UDP 流量均已经过网关。

如果无法确认，显示「未验证」。

### 3.7 连接延迟检测

分别测量：

- 本地至云服务器的 SSH 连接建立耗时。
- SOCKS5 连接建立耗时。
- 通过网关建立 HTTPS 连接的耗时。
- 目标测试服务的整体响应耗时。

将以上指标分开显示。

不得将 HTTP 响应耗时直接标记为纯网络 RTT。

支持显示最近一次检测值，并提供可选的历史趋势。

## 四、异常诊断与提示

根据实际检测结果输出相应提示。

| 异常情况 | 用户提示 |
|---|---|
| SSH 连接失败 | 检查服务器地址、端口、网络与认证配置 |
| 本地 SOCKS5 端口未监听 | 网关未正常启动 |
| SSH 进程存在但代理不可用 | 网络隧道异常，建议重新建立连接 |
| 网关出口 IP 不匹配 | 当前请求可能未使用预期出口 |
| Codex 连接命中其他节点 | 检查应用分流规则及代理冲突 |
| DNS 解析失败 | 检查 DNS 配置和目标域名解析 |
| IPv6 路由未验证 | 无法确认 IPv6 流量是否使用网关 |
| 目标服务返回 HTTP 503 | 远端服务或中间网络可能异常，需要结合响应来源进一步排查 |
| OAuth 返回 HTTP 401 | 认证失败，不能直接判定为网关故障 |

网络诊断模块只负责报告连接事实和可能原因，不应根据单次 403、401、429 或 503 错误直接判断账号是否被风控。

## 五、日志与隐私保护

日志只记录：

- 检测时间及持续时间。
- 网络连接结果。
- 必要的进程名称和连接路径。
- 实际出口 IP。
- HTTP 状态码及错误类别。
- 已脱敏的诊断信息。

默认不得记录：

- OAuth Token、API Key、Cookie 和 SSH 私钥。
- 完整 HTTP Header。
- 用户提示词、聊天记录或模型响应正文。
- 未经用户确认的完整 URL 查询参数。
- 其他应用的无关网络内容。

导出诊断报告前，对账户标识、私有路径、服务器凭据等信息进行脱敏。

## 六、开发实施顺序

M1：实现 SSH 隧道检测、本地 SOCKS5 测试和出口 IP 检测。

M2：实现服务器连通性检测及基础故障分类。

M3：接入 Mihomo 只读连接信息，完成 Codex 客户端进程与路由关联。

M4：实现 DNS、IPv6 检测和独立的客户端验证结果。

M5：实现可视化诊断页面、脱敏日志导出及自动化测试。

先确保 M1 能真实检测网络连接，再逐步开发后续功能。

不要第一版就开发 Windows 内核驱动或重新实现完整的 VPN 网络栈。

## 七、验收标准

1. SSH 隧道已连接但 SOCKS5 无法转发时，能够识别异常。
2. 本地出口 IP 与网关出口 IP 能够独立检测。
3. Codex Desktop、CLI、IDE 插件分别显示真实的验证结果。
4. 无法确认客户端路由时，不得显示为已验证。
5. 网络断开后不会使软件无限重试或卡死。
6. 不修改服务器现有 Docker、Nginx、CPA 和 SSH 服务配置。
7. 不覆盖用户原有 Clash Verge / Mihomo 配置。
8. 不读取、保存或导出任何账号认证凭据。
9. 能生成可供用户排查问题的脱敏诊断报告。
10. 断开网关后，不影响 Windows 原有的网络设置和正常连接。

完成后应提供实际运行截图、测试记录和已知兼容性限制，不得仅通过模拟数据宣称功能已经实现。
